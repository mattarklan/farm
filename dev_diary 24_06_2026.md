# Development Diary

## Project Goal

The long-term objective of this project is to build an autonomous farm manager capable of making operational decisions with minimal human intervention. Rather than hard-coding behaviour for one specific farm, the architecture is intended to be generic enough that the same decision engine could eventually manage greenhouses, warehouses, construction sites or other autonomous systems simply by changing configuration and sensor inputs.

The philosophy from the beginning has been to separate **facts**, **decisions**, **safety**, and **execution** into independent layers.

---

# Initial Design

My original thought was to build a fairly traditional automation system consisting of a large collection of Python if/then statements.

For example:

```
if soil_moisture < threshold:
    irrigate()
```

While simple, this quickly became difficult to scale. Every new feature would require adding more nested conditions, resulting in duplicated logic and increasing maintenance difficulty.

It became clear that the project needed a layered architecture rather than a collection of independent scripts.

---

# State Model

The first major design decision was creating a strongly typed state model using Python dataclasses.

The state contains only measurements and observations.

Examples include:

* battery state of charge
* tank level
* soil moisture
* temperatures
* humidity

Importantly, the state deliberately does **not** contain conclusions.

For example:

Good:

```
battery_soc = 15%
soil_moisture = 0.18
```

Bad:

```
needs_irrigation = True
battery_low = True
```

Those are conclusions which belong elsewhere.

Keeping state as "facts only" greatly simplifies reasoning throughout the rest of the system.

---

# Event Engine

The next layer converts raw measurements into meaningful events.

For example:

```
soil moisture = 0.18
```

becomes

```
S1_SOIL_MOISTURE_LOW
```

This allows later layers to reason about situations instead of individual sensor values.

One important design rule established here is:

> Only the Event Engine is allowed to interpret raw sensor values.

Everything downstream works with events.

---

# Rule Engine

Initially the Rule Engine consisted of hard-coded Python.

For example:

```
if event == LOW_SOIL_MOISTURE:
    irrigate
```

Although functional, this would require modifying source code whenever farm behaviour changed.

That approach was abandoned in favour of external configuration.

---

# Moving Rules into YAML

Rules are now stored in YAML files instead of Python.

Example:

```
Trigger:
    LOW_SOIL_MOISTURE

Condition:
    Battery > 20%

Action:
    Irrigate
```

The Python code no longer knows *how* the farm should behave.

Instead, it knows *how to execute rules*.

This separation means behaviour can change without modifying the engine itself.

It also opens the possibility of simulation, rule versioning, governance approval and eventually AI-generated proposals.

---

# Why YAML Instead of JSON?

One possibility considered was storing all rules inside JSON.

This was rejected.

JSON is excellent for structured data but poor for human-authored configuration.

Large rule sets become difficult to read because:

* no comments
* excessive punctuation
* limited readability
* cumbersome editing

YAML was chosen because it is significantly easier to maintain as the number of rules grows.

Rules are intended to be written and reviewed by humans, making readability more important than compactness.

Python support required installing the PyYAML package so the engine could parse the YAML configuration files.

---

# Constraints Layer

Originally safety checks were embedded directly inside rule logic.

Example:

```
if battery > 20:
    irrigate
```

This meant every irrigation rule would eventually need to duplicate the same safety logic.

That design was abandoned.

Instead a dedicated Constraints Engine was introduced.

Rules now express intent.

Constraints decide whether those intentions are safe to execute.

This keeps safety logic centralised rather than scattered throughout the project.

---

# Executor

The executor currently performs simulated actions by printing them to the console.

Examples include:

* irrigation
* load shedding
* alerts

Later this layer will communicate with real hardware.

The important point is that higher layers have no knowledge of hardware implementation.

---

# Logging

A logging system was added to record:

* complete farm state
* generated events
* proposed actions
* timestamps

Initially the logger attempted to serialise objects using Python's `__dict__`.

This failed because the project uses dataclasses with `slots=True`, which removes the `__dict__` attribute.

The logger was redesigned to use `dataclasses.asdict()`, which correctly serialises nested dataclasses and produces clean JSON suitable for replay and debugging.

---

# Current Architecture

The current decision pipeline is:

```
Farm State
      │
      ▼
Event Engine
      │
      ▼
Rule Engine
      │
      ▼
Constraint Engine
      │
      ▼
Executor
      │
      ▼
Logger
```

Each layer has a single responsibility.

---

# Design Philosophy

Several guiding principles have emerged during development.

### Facts are not decisions.

Measurements belong in state.

Interpretation belongs elsewhere.

---

### Behaviour should not require code changes.

Changing farm policy should involve editing configuration, not Python source.

---

### Safety should be centralised.

Individual rules should not contain duplicated safety logic.

The Constraints Engine exists specifically to enforce this.

---

### Every decision should be explainable.

The logging system exists so every action can be traced back through:

State → Event → Rule → Constraint → Action

No action should occur without an identifiable reason.

---

# Lessons Learned

The architecture changed significantly during development.

Several ideas that initially appeared simpler proved to be poor long-term solutions.

Examples include:

* embedding all logic directly in Python
* combining safety and decision logic
* storing rules in JSON
* directly serialising objects with `__dict__`

Each of these was replaced with a more maintainable solution after considering how the project would scale over several years rather than several weeks.

---

# Current Status

The project currently supports:

* structured farm state
* event generation
* YAML-driven rules
* safety constraints
* action execution
* execution logging

Although still a prototype, the core architecture has now been established.

Future development can focus on adding capabilities rather than redesigning the foundations.

---

# Long-Term Vision

The long-term objective is to create a management system capable of supervising an agricultural property with minimal human intervention.

Rather than replacing people entirely, the system is intended to act as an autonomous manager that:

* monitors conditions
* plans work
* allocates tasks
* supervises resources
* learns from historical performance
* proposes improvements while remaining subject to governance and safety constraints

Ultimately, the goal is not simply to automate irrigation or monitor sensors, but to build a decision-making system capable of managing a productive farm over many years while continuously improving its operation.
