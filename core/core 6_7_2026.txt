# Core (Farm Operator) — Devlog

This supersedes any earlier devlog in this repo — a lot has changed. Written
assuming you're picking this up fresh, possibly at the same time someone else
is working on ingestion — see the "Coordination with ingestion" section at the
end for exactly what that side owes this one and vice versa.

Status: runs clean against `python -m core.test` (fully mocked). As of this
writing, about to run its first continuous test against the **real** live
ingestor for the first time — everything before that point was tested against
mocked data or once-captured real samples, never a live continuous feed.

---

## 1. What core actually does, end to end

Every cycle (interval configurable, see `main.py`):

1. Pull current sensor state from the ingestion API.
2. Run sensor-health checks (confidence, staleness, out-of-range) — these can
   downgrade a sensor's trust to zero for the rest of *this same cycle*, so
   everything downstream automatically stops relying on a bad reading.
3. Evaluate threshold rules → typed Events.
4. Run/update multi-cycle goals (interruptible actions like irrigation) and
   generic cross-sensor anomaly checks.
5. Turn events into proposed instant actions.
6. Filter every proposed action through safety constraints (the one thing no
   rule source — yours, governance's, FOIS's — can bypass).
7. Execute allowed actions (config-driven, no hardcoded action types).
8. Deduplicate/annotate all events from the whole cycle through one shared
   policy (first-fire, periodic reminders, daily occurrence counts).
9. Export to GUI-readable files, log only genuine problems, persist evidence
   for anything explicitly flagged as needing to survive normal retention.

## 2. File structure and what each file does

```
core/
  models.py              Shared dataclasses: SensorState, Event, Action, ActionResult.
  severity.py             1=CRITICAL 2=URGENT 3=REVIEW 4=INFO scale, used everywhere.

  api_client.py            HTTP client for the ingestion API (GET /state/latest,
                           POST/GET /events, stub for future /weather/offsets).
  state_builder.py          API response -> the `state` dict everything runs on.
                           Splits any 2-element list/tuple metric (e.g. a
                           future GPS (lat,lon) pair) into two plain numeric
                           sensors, since nothing downstream handles tuples.
  registry_adapter.py        Wraps the real config/loader.py's plain-dict
                           registry into the object interface
                           (asset.id/.type/.metadata/.dependencies/.downstream,
                           get_asset_from_sensor()) the engines expect.

  event_engine.py             Sensor readings -> Events, via event_rules.yaml
                           thresholds. Skips sensors with confidence <= 0.
  confidence_monitor.py        Sensor health: zero-confidence (ingestor's own
                           "no signal" flag) and stuck-value detection
                           (volatility==0 for N cycles, heuristic). Both
                           DOWNGRADE the sensor's confidence to 0 in state,
                           not just raise an event -- that's what makes
                           everything downstream actually stop trusting it.
  staleness_monitor.py          Flags + zeroes confidence on sensors that
                           haven't reported within their configured max age
                           (config/staleness_thresholds.yaml, per-metric).
  range_monitor.py               Flags + zeroes confidence on physically-
                           impossible readings (config/sensor_range_thresholds.yaml,
                           per-metric min/max -- metrics not listed = no check).
  calibration.py                   Manual handheld-vs-sensor drift check,
                           on-demand (NOT wired into the main loop -- call it
                           yourself when you've taken a physical reading).

  rule_engine.py                   Instant (one-shot) Events -> Actions, per
                           rules.yaml. Uses goal_engine.infer_is_goal() to
                           skip anything that's actually a goal-kind rule.
  goal_engine.py                     Multi-cycle interruptible goals (e.g.
                           "water until moisture hits target, or 2h pass, or a
                           constraint trips"). THE most complex file -- see
                           section 3 below for the concepts it introduces.
  rule_watcher.py                     Watches rules.yaml for changes (OS-level
                           file notification via `watchdog`, falls back to a
                           slow poll + logged warning if not installed) and
                           triggers a live reload -- no restart, no lost
                           in-flight goal state.

  anomaly_engine.py                    Generic, YAML-driven cross-sensor /
                           commanded-vs-actual / action-effect checks
                           (config/anomaly_rules.yaml). Four rule types --
                           see section 4.
  constraint_engine.py                  Final safety gate. Blocks/delays
                           proposed actions per constraints.yaml.
                           action_types.yaml's `always_allow` flag makes
                           off/safe actions (CLOSE_VALVE, STOP_PUMP,
                           LOAD_SHEDDING, ...) bypass this entirely -- turning
                           something off is never blockable, by design.
  executor.py                            Dispatches allowed actions. Fully
                           config-driven (config/action_types.yaml) -- adding
                           a new action_type is a YAML edit, not a code change.
                           Currently only SIMULATES (prints) hardware effects.

  window_store.py                         Rolling time-windowed buffer of raw
                           sensor values (default 1h retention).
  derived_engine.py                        Computes slope/volatility per
                           sensor from window_store's history.

  #event_dedup.py                            Shared dedup/reminder/daily-count
                           layer -- EVERY event from every engine passes
                           through this before export. Individual engines
                           deliberately do NOT implement their own
                           one-shot/suppression logic anymore -- they report
                           honestly every cycle, this decides display
                           frequency. See section 5.
  #incident_recorder.py                       Permanent, never-pruned evidence
                           log (config/incident_log.json) -- triggered by any
                           anomaly rule with `record_sensors: [...]`. Not
                           vehicle-specific; reusable for any future
                           "this matters regardless of normal retention" case.
  gui_export.py                               Writes config/events.json
                           (90-day retention, 365 for CRITICAL) and
                           config/actions.json (30-day retention) for the GUI.
  logger.py                                    PROBLEM-only logger ->
                           logs/system.log. Routine operation is never logged
                           here -- only startup/shutdown, API-unreachable,
                           unhandled cycle exceptions, bad config files.

  pipeline.py                                   Orchestrates one full cycle,
                           in the specific order that matters -- see
                           section 6 for why the order is load-bearing.
  main.py                                        Entrypoint: wires everything,
                           runs the loop. CYCLE_INTERVAL_SECONDS is currently
                           set to 10 (test value, matching the test
                           ingestor's posting rate) with 60 (deployed value)
                           commented directly above it -- swap back for
                           real deployment.
  test.py                                         Smoke tests, fully mocked,

                           a top-level package relative to cwd).
```

## 3. `goal_engine.py` — the concepts worth understanding before touching it

A rule becomes a goal-kind rule (handled here, not by `rule_engine.py`) three
ways: explicit `until` list, auto-derived from a `duration_minutes` param with
no `until`, or `trigger: {type: schedule}` (wall-clock window, repeats daily,
no triggering event needed).

- **Templates**: `"$event"` resolves to the triggering event's asset/sensor
  (lets one rule cover every zone); `"$asset.<field>"` looks up that field on
  the target's own registry metadata (per-zone targets without per-zone
  rules).
- **Primary vs. fallback stops**: mark one `until` condition `primary: true`.
  Stopping via it is normal; stopping via anything else (timer, constraint)
  means the primary condition was never satisfied — automatically flagged
  (severity bumped, `expected: false`).
- **Confidence-aware**: a sensor-based `until` condition is skipped (not
  treated as met or failed) if that sensor's confidence is <= 0 — falls
  through to whatever else is in `until`, typically a timer.
- **FIFO resource queueing**: a rule can declare `resources: [bore_1]`. Two
  goals wanting the same declared resource — the second queues instead of
  silently failing, starts automatically once the first releases it. No
  priority preemption exists (deliberate — no real need identified yet).
- **Governance-aware**: respects `enabled`/`expires_at` on any rule, force-
  stops a running goal if its backing rule is disabled/expired/removed mid-run.

## 4. `anomaly_engine.py` — the four rule types

- `mass_balance` — a level should track the *direction* implied by inflow vs
  outflow (v1: direction only, not exact volume).
- `sensor_pair` — sensor A meeting a condition implies sensor B should too
  (e.g. bore running → flow > 0).
- `commanded_vs_sensor` — an asset commanded on via an active goal should show
  up on a related sensor.
- `action_effect_check` — an executed action should produce a measurable
  sensor change within N seconds (e.g. load-shedding should actually reduce
  current draw). Distinct from the other three: triggered by an executed
  action (`AnomalyEngine.on_action_executed()`, called from `pipeline.py`
  right after `executor.execute()`), not continuously re-evaluated.

New instances of all four are pure YAML. A genuinely new comparison shape
needs one new case in this file, after which it's reusable forever the same
way.

## 5. `event_dedup.py` — the policy, precisely

Key = `(event_type, asset_id, sensor_id)`. First occurrence emits immediately
and starts an "episode." While the same key keeps recurring, it's suppressed
except for a reminder every `reminder_seconds` (default 300s/5min). If a key
goes quiet for at least `cooldown_seconds` (default 300s, same number reused
deliberately) before reappearing, that counts as a genuinely new episode and
the daily count increments. Every emitted event carries
`data["occurrences_today"]` (resets at local AWST midnight) and
`data["is_reminder"]`. Whether a human has actually seen/acknowledged an event
is deliberately NOT built here — that's GUI-side, using the data this
guarantees.

## 6. `pipeline.py` — why the cycle order matters

Health checks (`confidence_monitor`, `staleness_monitor`, `range_monitor`) run
**before** `event_engine` and `goal_engine`, not after — this is load-bearing,
not stylistic. They can zero a sensor's confidence, and that needs to affect
*this* cycle's threshold/until checks, not next cycle's. If you ever reorder
this file, this is the constraint to preserve.

## 7. Config files, one-line purpose each

```
config/event_rules.yaml            Threshold rules (event_engine.py). Numbers
                                    are UNVALIDATED against continuous live
                                    data as of this writing -- watch closely.
config/rules.yaml                  Instant + goal rule definitions.
config/constraints.yaml            Locked safety rules (constraint_engine.py).
config/action_types.yaml           Action_type -> hardware channel mapping +
                                    always_allow flags.
config/staleness_thresholds.yaml   Per-metric max-age before SENSOR_STALE.
config/sensor_range_thresholds.yaml Per-metric physical min/max before
                                    SENSOR_OUT_OF_RANGE. Deliberately sparse --
                                    unlisted metrics get no check rather than
                                    a guessed bound.
config/anomaly_rules.yaml          The 4 anomaly rule types, real instances.
config/event_catalog.yaml          Reference doc: every event_type + default
                                    severity, for the GUI and rule authors.
config/weather_offset_schema.yaml  Locked schema for a not-yet-built future
                                    weather module.
```

## 8. Known gaps, honestly ranked

**Would actually bite you:**
1. `event_rules.yaml` thresholds unvalidated against a live, continuous feed.
2. Dependency chain (`crops.yaml` needs `dependencies` — requested from
   ingestion, see `INGESTION_REQUESTS.md`) has no code walking it yet even
   once the data exists — `prevent_bore_run_dry`/`prevent_tank_overflow`
   still unbuilt.
3. `_check_derived` (rate-of-change constraints) never got the `{target}`
   templating `_check_raw` has — a generic flow-spike constraint needs one
   copy per zone today.
4. No process-level supervision — a crash just stops core. Full design
   exists (`PROCESS_SUPERVISION.md`) but nothing's implemented.
5. GPS geofence built entirely on a guessed field name/shape — see
   `INGESTION_REQUESTS.md` item 7.

**Structurally incomplete, not just missing a rule:**
6. No genuine sensor redundancy (failover to a second physical sensor) — only
   graceful degradation (stop trusting, fall back to timer) exists.
7. No trend-based estimation for a sensor gone bad (e.g. dead-reckon a
   temperature forward from its recent slope) — deliberately not built,
   needs careful per-sensor-type scoping, not a quick add.
8. No startup reconciliation — a restart doesn't check whether core's belief
   about hardware state matches physical reality (e.g. "is this valve I think
   is closed actually closed").
9. Concurrency is FIFO-only, by deliberate choice — revisit only if a real
   preemption need actually surfaces.

**Smaller, noted:**
10. `interruptible`/`minimum_runtime_minutes` in `action_types.yaml` are
    recorded but unused — nothing can currently interrupt a running action
    from outside except its own conditions, so there's nothing for these to
    protect against yet. Deliberately kept rather than removed, per explicit
    decision, in case preemption ever gets built.
11. `set_irrigation_schedule` (from governance's draft schema) has no clean
    mapping yet — probably closer to "a `trigger: schedule` that supports a
    frequency pattern beyond daily" than a new mechanism, per discussion, but
    not designed in detail.
12. `decision_memory.py` was removed entirely (confirmed dead weight — nothing
    consumed its escalation scoring, and gui_export.py's persistent JSON
    already covers what its raw history provided). If you're wondering where
    it went, that's why.

**Written up in full, not built:**
13. `PROCESS_SUPERVISION.md` — crash/hang recovery design.
14. `PHASE_2_TREND_DETECTION.md` — multi-day degradation detection design
    (the "battery gets worse overnight, progressively" class of problem).
    Explicitly blocked on real trend data existing to validate against, and
    on ingestion's `/trends/hourly`/`/trends/daily` actually being called
    (see `INGESTION_REQUESTS.md` item 8).

**Deliberately out of scope, not gaps:**
15. Task assignment (fence checks, non-sensor-triggered scheduled work).

## 9. Coordination with ingestion

The other developer has `INGESTION_REQUESTS.md` — the short version of what
that means for you:

- **Don't build the dependency-chain walker or tank/bore-dry constraints
  until `crops.yaml` actually has `dependencies` populated** — building
  against absent data just means testing against nothing.
- **The `downstream` registry field is already live on both sides** (their
  `config/loader.py`, your `core/registry_adapter.py`) — you can use
  `asset.downstream` today, no coordination needed for that one.
- **Don't finalize the geofence rule's sensor names** until they confirm the
  real GPS field — what's in `anomaly_rules.yaml` now is explicitly a guess.
- **Phase 2 (trend detection) is blocked on them confirming `/trends/hourly`
  and `/trends/daily` are real and working** — no point starting that work
  before knowing the data's actually there.
- If sensor naming bugs (item 1–2 in their doc) get fixed at the source, some
  of core's defensive "unregistered sensor, just ignore it" handling becomes
  unnecessary — not urgent to clean up, but don't be surprised if those code
  paths quietly stop triggering once ingestion's fixes land.
